# Office UI conventions

These rules apply to all work under `office/`.

## Tables

- Use `OfficeActionHeader` and `OfficeActionCell` from `src/OfficeTable.jsx` for the final action column of every data table. They apply the global `office-action-column` styling: sticky right edge, 80px width, centered trigger, and matching header/row backgrounds. Keep the header visually empty with its accessible Actions label.
- Put row actions inside the shared `RowActions` menu. Give destructive menu buttons `className="danger-button"`. Do not create page-specific action widths, alignment, or menu designs.
- Use `OfficeTablePagination` from `src/OfficeTable.jsx` for every paginated Office table. Its global layout comes from the Businesses table: matching row range on the left; Rows per page and First/Previous/Page/Next/Last icon controls on the right. Use the shared 10/25/50/100 page sizes and ensure the API supports them. Pages without pagination do not need a footer.
- Pagination state remains owned by the page. Page-size changes reset to page 1; use the page and last-page values returned by the API after filtering or deletion. Pass the page's busy state to `disabled` during mutations where pagination must be blocked.
- Keep these patterns in `src/OfficeTable.jsx` and `src/office-table.css`. Change the shared implementation when changing the global design; do not copy its markup or override it per page.
- Preserve list data, search, filters, pagination, and scroll when returning from a detail/form page. Verify menu actions, pagination boundaries, page-size changes, and Back navigation using existing tests and isolated UI fixtures.
- Platform customer View/Edit uses a modal over the mounted list; New customer uses its existing full-page form. Preserve this distinction when revising that flow. Dismissing the edit modal must not refetch or replace the list, and a successful edit should reconcile the affected row.
- Shop report review uses `OfficeModal` over the mounted reports list. Keep its draft and nested View business return flow, reconcile saved report rows, and preserve search, filters, pagination and scroll when the modal closes.

## Search, primary actions, and filter drawers

- Use the shared app bar in `src/main.jsx` for new list screens. Follow the Businesses/Payment/Shop reports placement: navigation controls on the left, `office-appbar-search` immediately after them, and `office-topbar-actions` aligned to the right. Keep the page title and description in `office-page-heading` below the app bar.
- Reuse `office-appbar-search` and its existing rules in `src/desktop-parity.css`: compact search icon when empty, expansion on focus or when populated, leading Search icon, accessible input label, and a trailing clear button shown only when populated. Use `has-value` when populated. Enter submits the search without document navigation; clear resets only the search and page, preserving other filters. Preserve existing debounce behavior where provided.
- Place the page's primary Create/Add action in `office-topbar-actions` using `office-button-primary`, a Plus icon, and a specific label. Put the Filters trigger in the same action group using `office-filter-trigger`, a Filter icon, `aria-haspopup="dialog"`, and `aria-expanded`. Keep Refresh as the final control using the existing shared handler and busy state. Show an `office-filter-count` badge for non-default applied filters where relevant.
- Reuse `FilterDrawer` from `src/FilterDrawer.jsx` for advanced filters. It opens from the right, includes a backdrop and accessible title, manages keyboard focus, closes through its close control/Escape/backdrop, and restores trigger focus. Pass `busy` for mutations that must block dismissal. Keep filters out of a second inline toolbar above the table.
- Follow the Businesses drawer structure: `office-drawer-filter-form`, `office-drawer-filter-fields`, and the bottom `office-drawer-filter-actions` with Clear on the left and primary Apply filters on the right. Initialize draft fields from applied filters when opening. Apply commits the draft, resets page to 1, preserves search/page size, and closes. Clear resets drawer-owned filters, preserves search/page size, resets page to 1, and closes. Dismissal leaves applied filters unchanged.
- Keep search and applied filter state in a stable owner shared by the app bar and retained page. Preserve it across detail/form navigation and Back. Close the drawer when switching Office sections and avoid displaying controls belonging to a hidden retained page.
- Use `OfficePageToolbar` from `src/OfficePageToolbar.jsx` to render page-owned search and actions into the shared `OfficeAppBarContext` slots. It hides controls for inactive retained pages and when its `visible` prop is false (for example, during a form). Use `OfficeStatusFilterDrawer` for status-only filters or the shared `FilterDrawer` for larger forms. Platform users and Tutorials are working examples. Verify search/clear, primary action, drawer open/close, Apply/Clear, Refresh, and return-state retention when implementing or migrating these controls.
